# 自动化任务与业务触发执行模型

> 状态：第二版实现基线（2026-08-27）。本文记录当前已经确定的产品边界和运行契约，后续修改需同步更新本文。

## 1. 为什么不继续扩展画布工作流

当前核心诉求是“把一个脚本放到指定节点可靠执行”，不是在平台内重新实现一种编程语言。条件、并行、输入输出和复杂分支继续堆进画布，会与一个完整 Shell/Go/Python 脚本的能力重复，并增加维护成本。

因此第一版以 **自动化任务** 为执行单元：

```text
代码资产（在线脚本/Git 仓库） + 执行节点（位置） + 运行环境（输入/密钥） + 执行保护（超时/重试）
                                      ↓
                                  自动化任务
```

原工作流数据和接口暂时保留兼容，但不再作为自动化中心主入口，也不再是故障自动化处置的新建目标。

## 2. 模块边界

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| 在线脚本 | 单文件 Shell/Python 内容、运行方式、启停 | Git 仓库、绑定机器、故障匹配 |
| Git 仓库 | 仓库地址、默认版本、平台侧访问凭据、启停 | 入口文件、工作目录、执行命令、绑定机器 |
| 节点管理 | SSH/Agent 连接与执行能力 | 选择业务脚本、告警判断 |
| 自动化任务 | 选择在线脚本，或选择 Git 仓库并配置版本、工作目录、执行命令；绑定节点、运行环境、超时、重试 | 判断何时出现故障、管理通知渠道 |
| 故障中心/自动化处置 | 匹配故障、触发任务、冷却、静默/抑制、结果通知策略 | 保存脚本内容和节点凭据 |
| 通知管理 | 通知对象、模板、投递记录 | 决定哪个业务事件需要通知 |
| 域名/证书资产 | 域名监测和证书材料 | 远程执行步骤和通知渠道 |

自动化任务由手动执行、故障处置或脚本拨测触发。脚本拨测只引用自动化任务，保留调度和告警策略；脚本、节点和超时统一由自动化任务管理。

## 3. 普通脚本输入契约

### 3.1 脚本来源

代码资产支持两种来源：

- 在线脚本：适合单文件、小型 Shell/Python 脚本，内容保存在脚本库。
- Git 仓库：适合包含多个目录、模块和多个运维能力的综合项目。仓库本身不配置入口，一个仓库可以被多个自动化任务复用。

Git 仓库只保存代码来源及平台访问方式：

Git 仓库契约：

```text
name:             仓库名称
repository_url:   HTTPS、SSH 或 git@host:path 地址
default_ref:      默认分支或标签，可空
credential_type: none | token | ssh_key
```

具体执行方式属于自动化任务：

```text
source_type:       repository
repository_id:     Git 仓库 ID
git_ref:           本任务使用的分支或标签，可空（继承仓库默认值）
working_directory: 仓库内相对工作目录，可空（仓库根目录）
command:           例如 bash certificate/deploy.sh
```

工作目录不允许使用绝对路径或 `..` 逃离仓库。生产处置建议使用不可变标签；平台会在执行记录中保存实际 commit SHA 和制品 SHA-256。

### 3.2 Git 制品分发

目标节点默认不访问 Git，也不持有 Git Token 或 Deploy Key：

```text
Git 仓库
  → 平台使用加密保存的凭据浅克隆
  → 固定实际 commit
  → 排除 .git 并打包
  → 计算 SHA-256
  → 分发到执行节点
  → 节点校验、解压、执行、清理
```

- 平台本机：直接解压本地临时制品。
- SSH 节点：通过 SSH stdin 传输二进制压缩包，不把制品编码进 Shell 命令。
- Agent 节点：通过 `artifact_exec_v1` WebSocket 消息传输，要求 Agent `0.2.0` 及以上；Agent 校验摘要并安全解压。

仓库限制为最多 10,000 个文件、解压后 256 MB、压缩制品 64 MB。平台拒绝逃逸路径和指向仓库外部的符号链接。当前每次任务执行都会重新拉取；后续可按 commit SHA 增加共享制品缓存。

### 3.3 输入文件

平台把一次触发的完整输入序列化成 JSON，写入只在执行期间存在的临时文件，并导出：

```text
AIOPS_INPUT_FILE=/tmp/aiops-task-xxxxxx/input.json
```

在线脚本和 Git 项目的执行命令都可读取该文件。Shell 示例：

```bash
input="$(cat "$AIOPS_INPUT_FILE")"
domain="$(jq -r '.external_labels.domain // .labels.domain // empty' "$AIOPS_INPUT_FILE")"
echo "处理域名: $domain"
```

脚本的标准输出按原始文本保存。例如：

```bash
echo "hello"
echo "112233"
```

保存的 `output` 是 `hello\n112233`。平台不会猜测这两行是两个变量。需要结构化输出时，脚本应主动输出 JSON，未来消费者可按 JSON 解析；普通文本始终保持普通文本。

每种节点都有统一结果：

- `status`: `success` 或 `failed`
- `exit_code`: 成功为 `0`，失败为非零（当前远程执行第一版统一记为 `1`）
- `output`: stdout/stderr 汇总文本
- `error`: 平台或执行器错误
- `duration_ms`: 执行耗时

HTTP、通知等并不是画布节点；若脚本需要请求 HTTP 或发送业务通知，由脚本或对应业务模块完成。平台自身的“处置结果通知”仍通过通知管理投递。

## 4. 故障中心传给任务的 JSON

故障触发任务时，输入至少包含：

```json
{
  "event": "alert.firing",
  "trigger_status": "firing",
  "triggered_at": "2026-08-26T10:00:00+08:00",
  "alert": {
    "id": 123,
    "source": "probe-task",
    "source_id": 45,
    "title": "测试失败"
  },
  "labels": {},
  "datasource_labels": {},
  "external_labels": {},
  "last_result": {}
}
```

告警样例中的 `last_result.result` 可能还是一段 JSON 字符串。平台在写入输入文件前递归规范化：如果字符串本身是合法 JSON，就转换为对象或数组；普通字符串保持不变。

## 5. 结果通知

故障中心的自动化处置规则可以分别配置：

- 执行失败时通知（默认开启）
- 执行成功时通知（默认关闭）
- 通知对象

通知对象与模板仍由通知管理维护。通知失败只写通知记录，不反向改变已经完成的自动化任务状态，避免“处置成功但通知失败”被误判成处置失败。

## 6. 当前支持范围

- 旧 `workflow` 处置规则仍可由后端执行；新建或编辑规则只接受自动化任务。
- 证书管理和证书部署运行环境已移除，自动化任务只运行标准脚本或已同步的 Git 仓库代码。证书到期检查使用证书拨测。
- 独立定时任务已下线，新库不创建旧定时任务表；脚本周期检查使用脚本拨测。
- 旧版曾将 Git 地址和入口保存在脚本记录中；这些字段暂时保留读取兼容，新建 Git 项目统一使用 Git 仓库资产和自动化任务执行配置。
- 后续需要让 Agent/SSH 返回精确退出码，并将执行输入中的敏感字段做落库脱敏。
